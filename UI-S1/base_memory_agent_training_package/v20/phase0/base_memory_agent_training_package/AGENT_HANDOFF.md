# Coding Agent Handoff: Base-Derived Memory-Agent Full SFT

You are taking over a research experiment for multi-agent GUI control. The goal is to train multiple memory-specialized proposal agents from the base Qwen2.5-VL model and test whether their candidate union improves candidate-pool coverage beyond prompt variants of UI-S1.

## Core Research Idea

Current prompt-specialized candidate sources are all generated by the same UI-S1 SFT model, so their errors are correlated. We want to train separate full-parameter memory agents from the base model:

```text
Qwen2.5-VL-7B-Instruct -> full SFT memory-specialized proposal agents
```

The agents are not judged primarily as standalone policies. They are candidate proposal sources. The question is whether the union of their candidates improves coverage.

## Current Baselines And Targets

Known candidate-pool results before this package:

```text
UI-S1 alpha baseline TSR: 22.4%
Original memory-derived pool oracle TSR: 29.3%
Prompt-specialized targeted pool oracle TSR: 32.7%
Target oracle TSR: >= 35.0%
```

The trained full-SFT memory agents must be evaluated against the 32.7% expanded oracle reference.

## Critical Evaluation Rule

Do not confuse these two modes:

1. GT-history mode is only an offline coverage diagnostic.
2. Final deployment must be autoregressive.

GT-history answers:

```text
Can this trained proposal agent produce useful candidates at each true step?
```

Autoregressive deployment answers:

```text
Can the actual multi-agent system improve trajectory TSR when agents condition on the selector's executed history?
```

A valid result needs both:

```text
offline oracle coverage improves over 32.7%
autoregressive selector/aggregator trajectory TSR improves over current controller baselines
```

## Agents To Train

Train one full-parameter checkpoint per agent:

| RUN_KEY | Role |
| --- | --- |
| `type_recovery` | Type actions, field focus, focus-before-type, field binding. |
| `click_recovery` | Alternative grounded clicks, wrong/nearby target recovery. |
| `swipe_navigation` | Swipe, drag, scroll, navigation, reveal hidden targets. |
| `minimal_next_step` | Simple robust next action, broad proposal coverage. |
| `escape_finish` | Modal escape, finish guard, avoid premature FINISH. |
| `spreadsheet_formula` | Spreadsheet/cell/formula/table editing proposals. |

Each agent has exactly 2000 train and 300 dev examples in this package's expected data layout.

## After Training

For each trained checkpoint:

1. Export/merge into a vLLM-loadable model path.
2. Run official v13 GUI-360 evaluator in GT-history mode to generate candidate outputs.
3. Add these outputs to the candidate pool and run `analyze_oracle_reranker.py`.
4. If oracle improves beyond 32.7%, evaluate autoregressive selector/aggregator deployment.

Do not report GT-history oracle as final deployed performance.

## What Not To Do

- Do not start from UI-S1 for this experiment; start from base Qwen2.5-VL.
- Do not train only a single combined agent and call it multi-agent specialization.
- Do not treat standalone agent TSR as the main metric.
- Do not claim success from GT-history only.
- Do not overwrite existing UI-S1 or baseline model directories.
